## Closing the gaps of the clone and build output work (2026-11-19)

- Same-second edits: `policy::Tracked` now also keeps the nanoseconds of each index entry and compares them when Git stored them (Git writes 0 without nanosecond support; a stored value of 0 is not compared). `Index::matches_checkout` also refuses a tracked file modified at or after the index was written, which Git itself calls racily clean and checks by content. Together they cover a same-size edit within the second of the index write. A clone whose times moved only by nanoseconds while Git ignored them is now kept out; that only loses a suggestion.
- `CARGO_TARGET_DIR` is tested end to end through the binary, so the variable stays in a child process: `a_shared_cargo_target_folder_is_found_only_where_cargo_target_dir_points` (found under a hidden folder when the variable names it and it holds `CACHEDIR.TAG`; a relative value, another tagged folder and the folder without its tag are not).
- `catalog.rs` (3,731 lines) is split: `catalog/projects.rs` (clones, project output, project activity), `catalog/toolchains.rs` (toolchains, old versions, editor extensions, conda), `catalog/apps.rs` (application caches, data and leftovers, logs and temp), `catalog/downloads.rs` (installers, older copies) and `catalog/stores.rs` (store rules, unrecognized stores, rule drafts). `catalog.rs` keeps parsing, signing, findings assembly and ignores (1,674 lines). Items keep their paths through `pub use`; a line count of the moved code shows only the new module lines and formatting changed.
- Measured on the development home folder (macOS 27.2.1, Apple silicon, release builds, 582,607 entries, a partial scan with 438 folders the terminal may not read): `omg findings` took 0.23 s real, 0.15 s user with both `main` (`feab704`) and this branch, three runs each after a first cold run of `main` at 1.07 s. This branch found one more `project_build_output` item, a 441 MiB `coverage` folder of a JavaScript project. Three calls to `Index::findings` in one process took 154 ms, then 0.45 ms and 0.37 ms from the 60 second memo.

Verification: `cargo fmt --all -- --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings` in both builds; `TMPDIR=$(cd "$TMPDIR" && pwd -P) OMG_REQUIRE_DISK_IMAGES=1 cargo test --workspace --locked` (174 passed). `local_changes_older_than_the_last_index_write_keep_a_clone_out` gained a `retimed` clone (same-size edit, time put back within the same second); with the nanosecond comparison disabled it was suggested.

Not passed: the racily clean rule has no test of its own, because a test cannot set a file's change time and the change-time check already covers every edit a test can make. Linux and Windows run in CI only.

## Clones checked against Git's index, more build output, faster findings (2026-11-19)

- `unused_clone` false positive fixed. `policy::pristine_clone` relied on change times after the last index write, so a file edited, added or removed before Git last wrote its index (for example before a `git pull` or `git status`) could leave a clone with real local work suggested for deletion. It now also parses `.git/index` (versions 2, 3 and 4, SHA-1 and SHA-256, bounded to 64 MiB) and returns the tracked files; `Index::matches_checkout` requires the scanned listing to match it exactly: every tracked file present, of the indexed kind, size and modification second, and no other file except tool output (`CLONE_NOISE`). Entries marked assume-valid, skip-worktree, intent-to-add or in a merge stage, and split or sparse indexes, keep a clone out. Only Git's own metadata is read, and Git is never run.
- A scripted `omg clean --category unused_clones` no longer deletes a repository when it is the only match: `one_at_a_time` now applies to every scripted plan, not only to plans of several items. The interface still deletes one repository at a time after its own confirmation.
- `project_build_output` also recognizes `.vite` and `.nyc_output` beside `package.json`; `coverage` beside `package.json` only with `lcov.info`, `coverage-final.json` or `lcov-report` inside (a report without them may be committed); `.vs` beside a `.sln` or `.slnx`; `Carthage/Build` beside `Cartfile` or `Cartfile.resolved`; `.swiftpm` beside `Package.swift` without a `configuration` folder (registry and mirror settings are the user's); `dist` and `build` of a monorepo package that has no `.git` of its own, when `.git` and `pnpm-workspace.yaml`, `lerna.json`, `turbo.json`, `nx.json` or `rush.json` are up to four folders above; and the folder an absolute `CARGO_TARGET_DIR` names when it holds Cargo's `CACHEDIR.TAG`, judged by its own newest change because it belongs to no one project. `policy::REGENERABLE` gained `.vite`, `.nyc_output` and `.vs`; `cleanup::proven_build_output` gained `Carthage/Build` and `.swiftpm`.
- Maintainability and cost: four copies of the entry lookup in `findings_in` now call `Index::entry_at`. `unused_toolchains` reads `dir_totals` once for all toolchains' project folder names instead of once per name. `findings_in` keeps the last full list for 60 seconds, keyed by the published scan, catalog digest, ignores, arguments, home and SQLite's `data_version` (so a scan by another process invalidates it); a delete clears it. This saves repeated work in the interface, which lists findings after every change; a single CLI call is unchanged.

Verification (macOS 27.2.1, Apple silicon, Rust 1.95.0): `cargo fmt --all -- --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings` in both builds; `TMPDIR=$(cd "$TMPDIR" && pwd -P) OMG_REQUIRE_DISK_IMAGES=1 cargo test --workspace --locked` (173 passed); `cargo test --workspace --no-default-features --locked` (107 passed); the PTY smoke tests with a canonical `TMPDIR` (OK, 3 skipped); `node --test packages/oh-my-gigabytes/test/release.test.js` (21 passed). New tests: `local_changes_older_than_the_last_index_write_keep_a_clone_out` (an edited, an untracked and a removed file each keep a pulled clone out; a pristine clone and one with a version 4 index are suggested; a skip-worktree entry keeps a clone out; with the new check disabled the first three were suggested), `a_scripted_clean_leaves_a_whole_repository_for_review_even_when_it_is_the_only_match`, `test_coverage_bundler_caches_and_ide_state_are_found_with_their_project_file` (the new folders are found and delete; a committed-looking coverage report, `.swiftpm` with `configuration` and a package without a workspace file are not).

Not passed: the clone check compares sizes and modification seconds as Git's own racy-clean check does, so a same-size edit within the second of the index write is not seen (the change-time check still applies). `CARGO_TARGET_DIR` is not covered by a test, because setting an environment variable in the shared test process would affect other tests. The cost of findings on a large home was not measured for this change. Linux and Windows run in CI only. The section above closes these gaps.

## Deeper detection: project activity, removed apps, growth, unexplained space (2026-11-18)

Findings cover more languages and kinds of developer data, and say how recently a project was worked on. Nothing here grants deletion: every item still goes through `cleanup::verdict`, a confirmed plan and `delete_permanently`, and only home-folder paths are considered.

- Project activity: findings of project output (`project_build_output`, `stale_dependencies`) carry `activity` (`source`, `build`, `git`, Unix seconds) from the project's own listing: newest modification time of its files and folders, of its build and dependency folders, and of `.git`. The explanation says "project last worked on N days ago: files N days, last build N days, Git N days". `Index::suggest` does not add output of a project worked on within 7 days (`PROJECT_ACTIVE_DAYS`); it is still listed.

## Store rules and unrecognized stores (2026-11-18)

Owner decision 2026-11-18: signed catalog rules may describe where a tool keeps its own items, so a new tool can be supported by a catalog update without a new omg build. A rule never grants deletion: every item still goes through `cleanup::verdict`, a confirmed plan and `delete_permanently`.

- `catalog::Store` (`[rules.store]`), allowed only for the kinds `tool_sessions`, `tool_caches` and `tool_logs`. `parse` rejects roots outside the home folder's tool areas (`~/.<tool>`, the per-user data, config and cache areas, or an absolute environment variable), `..`, `.`, empty parts, character classes, more than 8 roots or 6 levels, and unknown fields. `store_root` checks again on the machine (`tool_root_allowed`, inside home).
- Matching walks one level per pattern by key (`parent=?`), so its cost follows the store, not the index. A search stops after 200,000 listed entries.
- Bundled store rules: Claude Code (`dev.ai-tool.session`, revision 2), Pi, Codex, GitHub Copilot CLI (`~/.copilot/session-state/<id>`, a folder), Cursor agent CLI (`~/.cursor/chats/<hash>/<id>`, a folder), Gemini CLI (`~/.gemini/tmp/<project>/chats/*.json*`). Each: 7 days unchanged, 1 MB or more, linux and macOS.
- `unrecognized_store` (`dev.unrecognized.store`, tier `info`, category `unrecognized`, never suggested): folders of 100 MB or more, up to 4 levels below the home folder's hidden folders, the application data areas and the cache area, found through `dir_totals` (only folders of 100 MB or more are listed), unchanged 30 days, with nothing protected inside, not at or around a known root or finding, and either named like a cache, log or temporary folder or holding 10 or more old files of one of `jsonl`, `ndjson`, `json`, `log` totalling 100 MB. At most 50.
- `omg catalog draft PATH` prints a rule for a store folder from folder listings only (no file contents, links skipped, at most 2,000 entries per listing and 20 subfolders), checked with `parse`. It needs a real source, fixtures and a signature before it can be imported.

Verification (macOS 26, Apple silicon, Rust 1.95.0): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `TMPDIR=$(cd "$TMPDIR" && pwd -P) OMG_REQUIRE_DISK_IMAGES=1 cargo test --workspace --locked` pass. New tests: `strict_catalog_and_tier_contract` (store rejections, glob, root resolution), `copilot_cursor_and_gemini_sessions_come_from_store_rules` (folder targets, one plan for all three), `big_old_stores_no_rule_knows_are_shown_but_never_suggested`, `catalog_draft_describes_a_store_from_folder_listings`. Timing: release build, a home folder of 511,500 entries, `omg findings` 0.15 s (three runs).

Not passed: store rules are tested with fake folders laid out as each tool's documentation describes, not with the tools' own output. The signed update channel (fetching new catalogs) is not built; catalogs are still imported by hand with `omg catalog import`. Store rules are not enabled on Windows.

## Delete around protected items, clearing lists, credentials in package code (2026-11-17)

Three problems found while testing 0.1.0 on the owner's Mac:

- `D` in OMG Trash, after "Delete everything except the protected items", planned only the folders that had protected items inside and dropped the rest of the selection. `DeletePlan` now carries `requested` (the OMG Trash ids it was made from, new JSON field) and `Index::prepare_delete_keeping_protected` takes the whole selection: folders with protected items are split into pieces, the other items stay as they were, and the same checks run on everything.
- The pieces of a folder deleted around protected items were each logged as their own line, and the folder kept its old size in OMG Trash. The Deleted log now has one line per folder (pieces add their size to it), and the folder's listed size is updated from the index after the delete.
- A folder or file named `credentials` was protected everywhere, which also caught package and test code (gRPC test sources in Cargo build-script output, `google-auth` in Python and Node packages). `credentials` is now not sensitive inside third-party trees only: `node_modules`, `site-packages`, `dist-packages`, uv's `archive-v*` folders, and `target/[triple/]profile/build/crate/out` (`policy::third_party_tree`, `policy::sensitive_name`). The same rule is used by `policy::hard_protection`, the descendant checks before a delete (Unix and Windows) and `Index::sensitive_inside`. Every other protected name (`.ssh`, `.aws`, `.gnupg`, `.git`, ...) and the key, database and `.env` suffixes stay protected inside those trees, and `credentials` stays protected everywhere else, including the rest of `target`.

The interface also gained `U` in OMG Trash (remove everything from the list, after a confirm; nothing is deleted) and, in Deleted, `u` (remove one line) and `U` (clear the log after a confirm), through `Index::forget_deleted`. The website demo has the same keys.

Verified on macOS 27 (APFS): `deleting_around_protected_items_keeps_the_rest_of_the_selection_and_logs_one_line_per_folder` and `credentials_folders_in_package_and_build_output_are_not_protected` (`tests/cleanup.rs`), `credentials_is_package_code_only_inside_third_party_trees` (`tests/policy.rs`), `capital_u_asks_then_clears_the_trash_list_or_the_deleted_log` (interface unit tests), and `cargo fmt`, `cargo clippy` (both builds) and `cargo test --workspace` (155 passed, with `OMG_REQUIRE_DISK_IMAGES=1`). Not checked: Linux and Windows (CI only).

## Interface themes (2026-11-15)

The interface has three themes: `auto` (default), `dark` and `light`. The choice is saved in the local `settings` table (`Index::theme`, `Index::set_theme`, no migration) and changed from the options menu (`m`, "Theme") or with `omg theme [auto|dark|light]`; `OMG_THEME` overrides it for one run. `auto` keeps the terminal's own background and picks the palette from `COLORFGBG` or, on Unix, by asking the terminal for its background colour (OSC 11) followed by a device-attributes request, reading `/dev/tty` without blocking for at most 400 ms before the interface starts, so a terminal that ignores the colour query leaves nothing behind as keystrokes. Windows without `COLORFGBG` uses dark. `dark` and `light` paint their own background in true-colour terminals; in 16-colour terminals they only change the text colours, and `NO_COLOR` stays monochrome. Themes change only how the interface is drawn. Verified on macOS 27 (APFS): `theme_cycles_and_a_chosen_light_theme_paints_the_screen` and `background_reply_picks_the_palette` (interface unit tests), the setting checks in `scans_suggest_regenerable_caches_but_never_large_files_and_respect_dismissal` (`tests/cleanup.rs`), the full workspace tests in both builds, the pseudo-terminal tests, and a pseudo-terminal run where a reply of a white background made `auto` draw the light palette. Not checked: real terminals other than the one used for development, Linux and Windows (CI only).

## Deleted log in the interface (2026-11-15)

Key `5` opens a fifth view, Deleted: a plain text record of what omg deleted (each fully removed target of a permanent delete, and each Docker item the engine removed) with its date and estimated size. Lines older than 20 days (`index::DELETED_LOG_DAYS`) are dropped when the log is written or read. It lives in a new table `deleted_log` (migration 014, schema 14); the `operations` audit trail, `omg history` and the freed total are unchanged. The log only records; nothing in it can be acted on. Verified on macOS 27 (APFS): `deleted_items_are_logged_with_size_and_dropped_after_twenty_days` (`tests/cleanup.rs`), `removed_docker_items_go_in_the_deleted_log_and_skipped_ones_do_not` (`tests/docker.rs`), `deleted_log_lists_date_size_and_escaped_path` and `key_five_opens_the_deleted_log` (interface unit tests), the schema 1..14 upgrade tests, and the pseudo-terminal test `test_a_cache_holding_a_protected_folder_is_deleted_around_it`, which now opens the log after a real delete and finds the removed folder and its size. Not checked: Linux and Windows (CI only), and a real Docker engine.

## Home scope needs a real home folder (2026-11-15)

Before this change an empty or `/` `HOME` (or `USERPROFILE`) made every scanned path count as inside the home folder, so `omg clean` and the interface could delete a project's `node_modules` anywhere on the volume. `platform::home` now refuses a home that is not absolute or is the filesystem root, and `cleanup::target_checks` denies every target when the home it is given fails the same check (`platform::usable_home`). Verified on macOS 27 (APFS): `HOME= omg clean ...` and `HOME=/ omg clean ...` against a fixture outside the home folder now stop with an error and delete nothing; new test `an_empty_relative_or_root_home_puts_nothing_in_scope` in `tests/cleanup.rs`.

## Catalog categories are fixed per discovery kind (2026-11-15)

`catalog::parse` used to accept any listed category for any discovery kind, so a signed catalog (or an edited `catalog_releases` row, which `Index::catalog` parses again without the signature) could file `large_file` or `huggingface_hub` under `package_caches`. Scans would then add those items to OMG Trash and `omg clean --category package_caches` would select them. `catalog::category_of` now gives the one category of each kind, and `parse` rejects a rule whose category differs. Verified on macOS 27: `strict_catalog_and_tier_contract` rejects the bundled catalog with `large_file` moved to `package_caches`, `build_artifacts` or `logs_and_temp`, and checks that every kind in `DISCOVERIES` has a category; the bundled catalog still parses.

## Old toolchain versions, logs and temp files, scripted clean, what grew, daily scans (2026-11-14)

Owner request (1.0 list items 5 to 12, without a release). Implemented:

- `toolchain_old_versions` (category `old_tool_versions`, suggested): direct folders of rustup `toolchains`, nvm `versions/node` and pyenv `versions`, grouped by line (Node major, Python major.minor, Rust release or nightly per target triple). ## Unused Docker data (2026-11-12)

Owner request. Docker's disk is never deleted (one file holds every image, container and volume); instead `omg docker` and the interface (`m` › Clean unused Docker data) ask the engine itself.

- Reached only locally: `DOCKER_HOST` if it is `unix://` or `npipe://` (anything else is refused), otherwise the known per-user sockets (Docker Desktop, Colima, OrbStack, Rancher Desktop, `/var/run/docker.sock`, rootless Docker and Podman) or `\\.\pipe\docker_engine` on Windows. A socket must be owned by the current user or root.
- Read: `GET /system/df`. Suggested by default: dangling images (no tag, no container) created 7 or more days ago and build cache not in use and unused for 30 or more days. Opt-in: tagged images no container uses and stopped containers, created 30 or more days ago. Never: volumes, running or paused containers, anything in use, or anything without a date.
- Removal: a fingerprinted plan the user confirms (the interface dialog defaults to Cancel; the CLI needs `--confirm <fingerprint>`). `Engine::remove` refuses if the plan is older than 15 minutes or if Docker no longer reports exactly the reviewed items, re-reads Docker before each item, and removes with `DELETE /images/<id>?force=false`, `DELETE /containers/<id>?v=false&force=false` or `POST /build/prune` filtered by id and `inuse=false`. `check_request` refuses every other request. Each removal is recorded in `operations` (kind `docker`) before it starts.

Verification on the development Mac (macOS 27.2, Rust 1.95.0): unit tests (request allowlist, remote hosts refused, HTTP chunked and sized bodies, RFC 3339 dates, classification and ages) and `crates/omg-core/tests/docker.rs` against a fake engine on a Unix socket (only planned items removed and without force; nothing removed when Docker changed or the confirmation is wrong; an item that comes into use mid-removal is skipped; opt-in kinds never include running containers). `cargo test --workspace` in both builds and clippy `-D warnings` pass.

Hostile engine replies (2026-11-15): a local socket answering `/system/df` with a build cache date of `2020-01-01T00:00:00+0é:00` made `omg docker` panic on a string slice, and image or volume sizes of `i64::MIN` or `i64::MAX` overflowed the size arithmetic (a panic in debug builds, a wrapped total in release). Dates are now read with checked slices, and sizes subtract and add with saturation. A tool output of more than 2000 bytes from `launchctl` or `schtasks` is also cut on a character boundary instead of panicking. Verified on macOS 27 against a fake engine on a Unix socket with all three replies (no panic, sizes saturate), and by the unit tests `dates_from_docker_are_read_exactly`, `extreme_sizes_from_an_engine_saturate_instead_of_overflowing` and `long_tool_output_is_cut_on_a_character_boundary`.

Not passed yet: a real Docker engine on any platform (no Docker was running on the development Mac), the Windows named pipe (compiled in CI only), and Podman's compatibility API.

## Apple and Windows signatures in the signing step (2026-11-13)

`scripts/platform-sign.js`, used by `sign-release.js` through `--apple-identity` with `--notary-profile`, and `--windows-signer`. Off by default; a release signed without them is unchanged. The platform signature is applied to a copy before the Ed25519 manifest, which covers the final bytes. An Apple identity without a notary profile is refused, as is a Developer ID signature without the hardened runtime or a timestamp, notarization that is not `Accepted`, and a Windows signer that leaves no certificate table.
