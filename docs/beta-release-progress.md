# Analysis-only beta: progress

Target: `0.1.0-beta.1`, Linux, Windows and macOS; Linux and Windows include permanent delete, declared `development-unqualified` (owner decision 2026-10-24, see the scope line below); macOS is analysis only. Status as of 2026-10-19, before that decision: **engineering complete for the analysis-only beta; not released.** The 2026-10-19 dry run below built the analysis-only variant, so it does not cover the delete-capable builds; those need a new `Release build` and `Install smoke test` run. Final dry run on commit `71b1538`: Checks green on all nine platform legs plus supply chain, release build run 39245775796 (five targets), install smoke run 39246347274 (eight machines). What remains is the owner's: production signing key, security contact, npm names and publishing, and the go-ahead to tag and publish. Nothing is tagged, uploaded or published, and no production signing key exists. **Update 2026-11-01:** the first run on a real Mac (Apple silicon, macOS 26.5.1) found and fixed four defects: unreadable and excluded folders shown as `0.00 B`, release assembly failing on a Mac (`/var` link), every dry-run preview on macOS calling present targets "stale", and the quarantine test's claim that is false on a real Mac; they passed `Checks` on all nine platform legs plus supply chain (run 41329117019 on commit `ead1d57`, which also has rusqlite 0.41.1, rustix 1.1.6 and sha2 0.11.1). The `Release build` and `Install smoke test` dry runs have not been repeated on that commit. Evidence lives in the platform pages: [linux-qualification.md](linux-qualification.md), [windows-evidence.md](windows-evidence.md), [macos-evidence.md](macos-evidence.md), [release.md](release.md).

Scope decisions (owner, 2026-10-18): analysis-only first (reversed for Linux and Windows on 2026-10-24, below); native macOS analysis adapter tested on GitHub-hosted runners; GitHub Releases plus npm, Ed25519 signing only (no Authenticode, no Apple notarization). Owner, 2026-10-24: release targets are Linux x64 and ARM64, Windows 11 x64 (Windows 10 is not a target) and macOS on Apple silicon only. The Intel Mac build was removed from the release workflow, launcher, signing and smoke matrix; the five-target and eight-machine runs recorded below predate that, and the changed workflows have not been run yet. **Owner, 2026-10-24: the Linux and Windows release binaries include permanent delete** (the default features); macOS has no delete and is built with `--no-default-features`. Delete stays `development-unqualified`: it is offered, labelled and documented as unqualified, never as safe.

## Pre-release review (2026-10-24)

Environment: WSL2 Linux x86_64 (kernel 5.15), Rust 1.95.0, Node 22.20.0, on `39953c2` (equal to `origin/main`). Nothing was tagged, uploaded or published.

- CI: `Checks` run 39246579532 on `39953c2` is green on all nine platform legs and the supply-chain job. The two ARM legs were read step by step: every step ran and passed (`continue-on-error` was not hiding a failure).
- Local gates, all passing: `cargo fmt --all -- --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings` in the default and `--no-default-features` builds; `cargo test --workspace --locked` in both builds; the Unix PTY smoke test; `node --test packages/oh-my-gigabytes/test/release.test.js` (19 of 19).
- Local end-to-end, Linux x64 only: built `--release --no-default-features`, signed it with a throwaway Ed25519 key through `scripts/assemble-release.js`, listed the offline package (`npm pack --dry-run`), and ran it through the launcher: `--version`, `doctor` (reports permanent delete unsupported), `scan`, `status`, `tree`. A binary with one byte appended was refused with "Binary integrity verification failed". The release binary only offers `cleanup --dry-run`. No secrets or key files are tracked.
- Fixed: the npm package README (shipped in every tarball) still said macOS and Windows analysis was "disabled pending certification"; `SECURITY.md` said Windows and macOS were "compile checks only" and that the product deletes files; the Linux ARM64 CI leg was `experimental` although `linux-arm64-gnu` is a release target, so it is now required; the 0.1.0 local-build section of `release.md` is marked superseded.
- Scope change (owner, 2026-10-24): Intel Mac (`darwin-x64`) removed from the release workflow, the launcher's target list, signing and the install-smoke matrix. The tests now expect four targets (and nine `SHA256SUMS` lines) and check that an Intel Mac is reported as unsupported; `release.test.js` passes 19 of 19 locally. The edited `release.yml`, `smoke.yml` and `check.yml` have not been run in CI yet. The `Checks` workflow still runs the Rust tests on `macos-15-intel` and the Arm Windows leg; they test code, not a release target.
- Fixed after a report from the owner's WSL2 session (2026-10-24): the interface said "Another omg scan is running; showing the last published results until it finishes" with no progress or timing while no scan was running. Cause: on every launch the interface prunes superseded scans on a background thread (`Index::prune_stale`, up to 120 s), which holds `scan.lock`; the interface treated any held lock as a scan, found no `running` row, stopped polling and left the message up. On the owner's 3.8 GB index the index and WAL files were written during the first seconds after launch, which fits. Now `PollRunning` also reports whether the lock is held; a held lock with no scan shows "Waiting for another omg task… Ns · no scan is running…", keeps polling, and runs a scan the user asked for (or the first-run scan) once the lock is free; Esc cancels it; a real scan from another process still shows its progress and estimate. Evidence: four new interface unit tests, and `tests/test_terminal.py` holds `scan.lock` with no scan, reads a reconstructed screen, presses `r`, releases the lock and checks the scan completes (1.3 s); the same test fails on the pre-fix binary, whose screen shows the old message. fmt, clippy (both builds), `cargo test --workspace` (both builds), the PTY tests and `release.test.js` (19 of 19) pass on Linux. That fix did not stop housekeeping from holding the lock for its whole run; see the next entry. Not run on macOS (the PTY test uses `flock`, which macOS supports) until CI runs it.
- Fixed after a second report from the owner (2026-10-24, delete-capable build): pressing `d` right after launch gave "⚠ a scan is running; wait for it to finish, then delete" and nothing was deleted. No scan was running. The old generation left by a full scan of `/` (1.35M entries) was being pruned by the launch-time housekeeping, which took about 50 s and held `scan.lock` for all of it, and delete takes the same lock. Now `Index::prune_stale` works in 300 ms slices and releases the lock for 150 ms between them, stopping at once if anything else holds it and resuming next time; `cleanup.rs` waits up to `LOCK_WAIT` (2 s) for the lock before refusing, so a lock held for a moment lets the delete through while a scan that really is running still stops it with the same message; the interface's own scan job retries briefly on Busy for the same reason. `scanner::scan` itself stays strict: giving it the wait broke `foreground_scan_takes_over_from_a_running_service_scan_without_corruption`, because the foreground scan must see Busy at once to ask the service to yield. Evidence: new `tests/housekeeping.rs` (lock wait, and a 400,000-row backlog where a waiting taker gets the lock while most rows remain; it fails if the slice is made as long as the budget, i.e. the old behaviour) and `delete_waits_out_housekeeping_but_a_running_scan_still_stops_it` in `tests/cleanup.rs`; on the real release binaries with a 400,000-row backlog and a delete issued after housekeeping had started, the previous build refused with the message above and the new build deleted at once, removing only the chosen file. Not done: the backlog is still cleared only while nothing else holds the lock, so a long delete or scan postpones it to the next launch; a full scan of a large disk still leaves a generation of that size to clear.
- Delete around protected items (owner request 2026-10-24). A cache folder with a protected name inside (the owner's `~/.cache/uv` holds six Python package folders called `credentials`, `~/.cargo/registry` one `Credentials` folder) was shown as "1 item" and then skipped at deletion with "contains a sensitive item", so nothing was deleted. Now: the plan detects protected names (`policy::ALWAYS_SENSITIVE`, the same list the deletion enforces) from the index and says so before confirming; for caches it offers "Delete everything except the protected items", which splits the folder into ordinary pieces (files and folders with nothing protected inside, never a protected item or the folders on the way to one) and asks again. `prepare_delete_keeping_protected` only plans; every piece is then validated and removed by the unchanged per-item deletion path, so a protected item that appears after review still stops its piece. Ordinary (non-cache) folders are refused with no such option. Also found and fixed while testing: dialogs sized their box for unwrapped text, so a long line hid the choices, including "Yes, delete permanently" (choices now have their own rows; regression test fails on the old code); and the per-item free-space query (`freed`) let SQLite scan the whole scan's identity index, about 1.1 s per call on the owner's index, which made planning 1,190 pieces take over 150 s; it now names the primary-key index (9.5 ms; planning takes 0.6 s; a unit test checks the plan). Evidence: four new `tests/cleanup.rs` tests (delete around a `credentials` folder, caches only, a protected item added after review, an unprotected cache stays one item), interface tests for the dialogs and the result line, a terminal test through the real interface (`test_a_cache_holding_a_protected_folder_is_deleted_around_it`), and a 1,200-package cache with one protected folder deleted through the real release binary in 2.2 s (plan 0.1 s). A read-only dry run on the owner's real index planned `~/.cache/uv` as 1,190 pieces keeping 6 folders, and `~/.cargo/registry` as 212 pieces keeping 1; nothing was deleted by the dry run. Freed space is about 2.7 GiB for uv and 320 MiB for cargo, not the listed 10.17 GiB, because uv hard-links its files into project environments. Not run: the Windows build of this planning code (it has no platform-specific parts, but only CI compiles it), and macOS.
- Delete in the release (owner decision 2026-10-24). Changed: `release.yml` builds Linux and Windows with the default features and macOS with `--no-default-features`, checks each binary's `doctor` against the capability its target should have and records it in a `CLEANUP` file; `build-manylinux.sh` takes the cargo flags; `sign-release.js` signs the capability from that file (a missing or unknown value stops it); `smoke.yml` expects `development-unqualified` on Linux and Windows and `unsupported` on macOS; the CLI help no longer says "analysis-only" in a delete-capable build; `omg doctor` no longer lists XFS among delete filesystems (the code refuses delete on XFS); README, npm README, `SECURITY.md`, `release.md` and `CLAUDE.md` describe delete and its limits. Verified locally on Linux x64 (WSL2, ext4): `release.test.js` 21 of 21 (new tests sign Linux and Windows as `development-unqualified` and macOS and any analysis-only build as `disabled`, and refuse a missing or unknown `CLEANUP`); and, on the real `--release` default-feature binary with `HOME` pointed at a throwaway folder, driven through a pseudo-terminal: Browse, `d` on a file, "Are you sure?" (Cancel is the default, the file is still on disk while the question is open), "Yes, delete permanently" removed exactly that file and left its neighbour; Esc at the question left the file; a `.pem` file in the same folder is refused with "cannot add to OMG Trash: database, disk image, credential or active download" and stays; the analysis-only binary answers `d` with "Permanent delete is not available in this build" and removes nothing. On CI at `39953c2` the seven Windows deletion tests ran (not skipped) and passed on windows-2022 and windows-latest, and the 19 Linux cleanup tests passed on ubuntu-22.04, ubuntu-24.04 and ubuntu-24.04-arm. Not done: a delete on a real Windows 11 or Linux ARM64 machine with the release binary; the changed `release.yml`, `smoke.yml` and `sign-release.js` have not run in CI. The same delete flow is now an automated test, `test_delete_removes_only_the_confirmed_file_and_refuses_protected_ones` in `tests/test_terminal.py` (throwaway `HOME`; passes on Linux here; skips itself on a build without delete, so on macOS; a Windows ConPTY version does not exist yet).
- Not verified here: Windows and macOS were not run natively on this machine (only the Linux standard library is installed); their evidence is the CI legs above. Advisories were last checked by CI on 2026-10-19; rerun `cargo deny check` before tagging.
